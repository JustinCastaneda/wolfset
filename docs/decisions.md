| 2026-08-22 | 11 | **Progression is a strategy enum; `steady` (progressive overload) is the default** | Three strategies, each a per-exercise setting with a plan-level default. **`steady`** — weight-based: hit every prescribed set/rep → next session adds a per-exercise increment (2.5–5 lb) and keeps climbing until a ceiling; that climb *is* the mesocycle, and a new mesocycle is how a plateau is broken. **`reps-first`** — rep-based: weight holds, reps climb week over week, then weight steps up. **`by-feel`** — user picks weight or reps each time; built last, least common. A mesocycle is therefore typed by its strategy (weight-based vs rep-based), not one shape. Justin's call. **Still to pin down (defaults proposed, not decided):** increment size (default 5 lb, per exercise), what ends a mesocycle numerically (proposed: 2 consecutive sessions missing the target → suggest a new meso), and whether "missed → drop 10%" (the rule on the Progression Override screen and in the brief) is the shared deload for every strategy or `reps-first`'s rule only — the Figma screen copy may need updating once that's answered. |
| 2026-08-22 | 11b | **Progression numbers pinned; plateau is a prompt, not an auto-action** | Justin: weight increment **5 lb default, per-exercise override** (some lifts want less). A mesocycle's plateau trigger is **two consecutive *failures*** — sessions done but below target — **not misses** (skipped days). At two failures the app **asks** whether to deload or end the meso and start a new one; it never decides alone. **Deload default: drop 10% after two failures, overridable per exercise** (some lifts need more or less). Also raised, not designed, not MVP-blocking: an **absence deload** offered on Workout A when the user returns after missing too much time; customisable later in settings. Justin designs it; the model already carries what it needs (`docs/data-model.md` §5.4). |
| 2026-08-22 | 11c | **Data-model questions answered** | Reps-first ceiling is user-chosen at setup ("Max Reps before Weight Increase": 12/16/18/20/custom, default 20) — Justin is adding the button group to the screen. Deload and every computed weight round to the **nearest loadable weight**, which depends on load type and the gym (barbell 5 lb steps with 2.5 plates; dumbbells 2.5 or 5) — a per-load-type smallest-step setting, onboarding later. Freestyle Session Done has two exits: **add as a new day to the current plan**, or **new mesocycle with this as Day 1** (double confirmation — it ends the current plan). Ending a workout early scores unfinished exercises as failures. |
| 2026-08-31 | 11d | **Figma review after Justin's design sprint: By Feel specified, absence deload designed, settings added** | **By Feel is an engine now** (`384:11049`): post-exercise 2D poke (form × reps-in-reserve, auto-skip 8 s), Step 1 maps poke → 0/1/2 steps, Step 2 lets the rep range (default 5–8, per-exercise) pick the lever (+1 rep per step below the top; at the top +weight and reps reset), past-session rules add deload 10% (bad form or two missed), add-weight (held at top twice), and offer-switch-to-Steady (unrated twice). **Absence deload**: trigger is **2 missed workouts** (not days), scope **all exercises**, 10%, Decline/Accept on Workout A. **Settings** let users change onboarding answers later; goal gains **Vibing**; personal settings add bodyweight & height; Exercise Data adds **export**. **Load types are six** (+ kettlebell, cable). Dumbbell smallest-step designed in onboarding (Unit & Scale) and settings. All 14 type styles became Variables — 3a unblocked. |

| 2026-09-02 | B | **"Recovered" = absolute heart-rate bands: green < 120 bpm · yellow 120–140 · red > 140** | Justin, after the first hardware run: 120 is a vigorous walk, so by then you've recovered; peaks sit ~165 for most people. Mirrors Fitbit's zones. Replaces the spike's peak-relative placeholder. These are defaults: they shift with age, so they become a Profile setting later, and the app may eventually learn them from when the user taps Continue. The rule still only colors the ring and arms Continue (brief §01). |
| 2026-09-03 | — | **The phone drives the watch stream; the watch is never tapped** | Start Workout starts the stream over the Data Layer (`/wolfset/control`), finishing or leaving the session stops it. The watch keeps its own Start/Stop as a fallback and stops itself after 3 hours if the stop never arrives. The stream runs exactly while the session screen is up — a resumed session restarts it — so a pocketed phone mid-set keeps streaming and an abandoned one cannot drain the watch. |
| 2026-09-03 | — | **The rest timer lives twice: JS is the truth, native holds it in the pocket** | The machine keeps absolute timestamps and ends the rest on screen; a native health-type foreground service holds the same rest through screen-off with a wake lock, a countdown notification, a buzz at the end and a buzz on "recovered", then hands "rest over" back to JS. Native never advances the loop (brief §01). Costs two runtime permissions on Android 13/14+ (notifications, activity recognition), asked once at the first workout; a refusal degrades to the on-screen timer. See `docs/rest-timer.md`. |
| 2026-09-03 | — | **Rest alerts are a buzz and a ding, the ding on the alarm stream** | Justin, after the first pocket run of the native timer: people lift with headphones on, and a ding is how Stronglifts and Fitbod say "lift again". Played by the service on the alarm stream so it sounds through headphones with the phone on vibrate; the notification channel stays silent to avoid a double ding. Same buzz + ding for "recovered" and "rest over" for now. |
| 2026-09-03 | — | **The rest alert is "rest over" only** | First watch run of #48: the "Recovered" buzz + ding fired the instant Justin logged a set because his heart rate was already under the threshold — noise, not a signal. Rule: **we only ding when the full timer is done; the user makes the call on whether they're recovered.** Recovery is still *shown* (green ring, Continue solid, phone and watch); the native `RestTimerService` no longer watches the heart-rate bus. `docs/rest-timer.md`. |
| 2026-09-03 | — | **Skip Set moves on without a log; it is not a set** | The watch's Actions panel needed a meaning for Skip Set that the machine did not have. Rule: a skip advances to the next set (or the next unfinished lift) exactly as the end of a rest does, but records nothing and starts no rest, so the lift scores short — a failure under data-model §5.1 — and the day's total stays honest. A skip can never auto-finish a workout; the loop comes back to the short lift. Only reachable while logging (during a rest, Continue is the skip). The watch's "End Workout?" is the double confirm for ending from the wrist; the phone does not ask again. |
